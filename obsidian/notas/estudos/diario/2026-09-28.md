# 2026-09-28

## O que fiz

Estudo de arquitetura (sem código): como dar autonomia ao time de EDI para
alterar manuais na tela sem que a alteração chegue ao cliente sem revisão.
Resultado em [`docs/arquitetura/estudo-fila-aprovacao-conteudo.md`](../../../../docs/arquitetura/estudo-fila-aprovacao-conteudo.md).

Levantei o que o portal já tem (editor, quality gate, adapter de leitura do
GitHub, campos de versão vazios), pesquisei como o mercado resolve e comparei
três desenhos possíveis para a fila.

## O que aprendi

- **O padrão do mercado tem nome:** *editorial workflow*. Decap, Sveltia e Tina
  fazem todos a mesma coisa — salvar na tela vira branch + Pull Request, e
  aprovar vira merge. Não precisamos inventar o mecanismo, só a interface.
- **Fila não precisa de banco.** Minha intuição era criar uma tabela de
  "alterações pendentes". Mas o estado do PR (aberto, label, aprovado, merged)
  já é exatamente esse estado. Guardar de novo criaria duas verdades que
  divergem no primeiro erro de rede — e ainda esbarraria no `requireDatabase()`
  de `core/db`, que bloqueia a capacidade `queue` de propósito (ADR-0002).
- **Contents API vs Git Data API.** Gravar arquivo por arquivo (Contents) pode
  deixar a branch pela metade se falhar no meio. Git Data API monta o commit
  inteiro antes de mexer na branch: ou entra tudo, ou nada.
- **Por que a fila vira um módulo novo (`modules/publicacao`)**: se ela morasse
  dentro de `living-docs-externa`, o módulo `manuais-internos` teria que
  importar outro módulo para usar a mesma fila — e `npm run arch` quebraria.
  A regra de arquitetura decidiu o desenho por mim.
- **Segregação de funções ("4 olhos")** é regra de servidor, não de tela:
  comparar o e-mail de quem enviou com o de quem aprova. Esconder o botão no
  front não é controle.

## O que travou

Nada travou — foi estudo. O ponto que levou mais tempo foi entender onde a fila
deveria viver, porque a resposta intuitiva (banco) era a errada.
