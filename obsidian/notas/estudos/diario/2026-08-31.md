## O que fiz
- **Suporte a REST no portal (para o PSP):** até hoje o portal só sabia falar
  GraphQL. Implementei o protocolo como conceito de primeira classe:
  - `manual.ts`: `kind: "rest"` + `method`/`path`/`exampleBody`, com
    `superRefine` exigindo `method`+`path` só quando `kind === "rest"`.
  - `project.ts`: `protocol: "graphql" | "rest"` (default `"graphql"`,
    preserva projetos existentes) + `apiBaseUrl` (equivalente ao
    `graphqlUrl`).
  - `manual-quality.ts`: checks `gateway` e `operacoes-exemplo` passam a
    olhar `apiBaseUrl`/`method`+`path` quando o projeto é REST.
  - `connect-api.ts` (novo) + rota `/api/.../connect-api` + `ConnectApiForm`:
    conecta a API REST **sem verificação automática** de credencial — o
    portal não conhece o endpoint de login de cada API legada, então
    inventar uma chamada de autenticação seria arriscado. Só cifra e grava.
  - `operation-detail.tsx`/`manual-roteiro.tsx`: operação REST mostra bloco
    "Endpoint" (`method path` + corpo de exemplo) em vez de "Exemplo
    GraphQL"/playground.
  - `export-postman.ts`/`export-insomnia.ts`/`export-pdf.ts`: geram request
    HTTP puro para operações REST.
  - `create-project-form.tsx`: seletor de Protocolo (GraphQL/REST) ao lado
    do de Família.
- **Reestruturei EDI Varejo em dois projetos:** `edi-canais` (GraphQL, um
  gateway só, seções por tema: credenciado, beneficiários, busca de preço,
  benefício farmácia) e `psp` (REST, gateway próprio). Ambos com introdução
  **real** migrada de `developer.funcionalmais.com` (GraphQL: queries vs.
  mutations, formato de erro, JWT; REST: JWT). O resto (regras de negócio de
  cada endpoint) fica marcado como pendente até receber o conteúdo do
  legado ou conectar o gateway real.
- Testes: `manual.test.ts` (novo, superRefine), `connect-api.test.ts` (novo),
  casos REST em `manual-quality.test.ts`/`export-postman.test.ts`, e E2E
  `rest-api-flow.spec.ts` (cria projeto REST → operação → publica → lê

## O que aprendi
- **`z.object(...).superRefine(...)` deixa de ser `ZodObject`** — perde
  `.extend()`/`.omit()`. Solução: manter uma "forma crua" (`ManualOperationShapeSchema`,
  só `z.object`) para derivar `createInputSchema`/`updateInputSchema` via
  `.extend()`/`.omit()`, e aplicar o `superRefine` em cada schema final
  separadamente (função `requireRestFields` reutilizável).
- **Union type "contamina" quem reusa o tipo:** ao adicionar `"rest"` em
  `ManualOperationKind`, o `PlaygroundAllowlistResult.kind` (que reusava esse
  tipo só pra "query"/"mutation") também passou a aceitar `"rest"` — quebrou
  o typecheck em `recordPlaygroundExecution`. Fix: parar de reusar o tipo de
  domínio onde o subconjunto é diferente; usar o tipo específico do
  playground (`PlaygroundOperationKind` de `core/metrics`).
- **REST não tem "erro no corpo"** como GraphQL — por isso a introdução do
  `/docs/psp` e do `/docs/intro` legados difere: GraphQL explica
  `errors[].message`, REST não precisa (o status HTTP já diz).
- **Segurança > funcionalidade:** decidi não simular login REST para validar
  credencial no connect — sem saber o endpoint real de cada API legada,
  "inventar" uma chamada de autenticação poderia bloquear conta ou validar
  contra o endpoint errado. Fica só cifrar/gravar; validação real na
  primeira chamada de verdade.

## O que travou
- `URL.toString()` normaliza adicionando barra final (`https://x.com` →
  `https://x.com/`) — o teste de `connect-api` esperava a URL crua; corrigi
  a expectativa em vez de "lutar" contra o comportamento padrão de `URL`.
